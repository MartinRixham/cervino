# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Bash script, `build-alpine-gnome-iso.sh` (with its apkovl generator `genapkovl-gnomelive.sh` and the AppArmor profiles in `apparmor.d/`), that builds a bootable x86_64 Alpine Linux live ISO that boots straight into GNOME, or with `TARGET=rpi` an aarch64 Raspberry Pi SD card image (`.img.gz`) of the same system. It reproduces what `setup-desktop gnome` would install and enable, on top of Alpine's "standard" ISO (or its `rpiimg` image). `README.md` documents the user-facing behaviour and the environment variables (`TARGET`, `ALPINE_BRANCH`, `OUTDIR`, `LIVE_USER`, `LIVE_PASSWORD`, `AUTOLOGIN`, `BROWSER`, `CONTAINER`, `MIRROR`). Keep the README table, the script's header comment and the workflow in sync when you add or change a setting.

## Build and test

There are no unit tests or linters. A change is checked by building the ISO and booting it:

```sh
./build-alpine-gnome-iso.sh                       # needs podman or docker, curl, network
ALPINE_BRANCH=v3.24 AUTOLOGIN=0 ./build-alpine-gnome-iso.sh
qemu-system-x86_64 -enable-kvm -m 8G -cdrom out/*.iso   # live system runs from RAM: ~6 GB+
ci/vm-test.sh out/*.iso                             # the end-to-end test CI runs
```

`ci/vm-test.sh` drives two QEMU/KVM boots over the serial console, keeping the logs in `$WORKDIR` (default `./vm-test`). First it boots the ISO's kernel directly, with the `APPEND` line from the ISO's `syslinux.cfg` plus `console=ttyS0` (the ISO's boot loaders have no serial console), and installs to `/dev/vda` with `ci/guest/install.sh`, which runs an answer file through the ISO's `setup-alpine` wrapper and then fails if the live system's kernel log has any AppArmor denials (`ci/guest/apparmor-denials.sh`). Then it boots the disk, logs in as `tester` (root is locked there; after installing, `install.sh` mounts the disk, clears tester's password, which the install leaves locked, and adds a `permit nopass tester` doas rule) and runs `ci/guest/test.sh` through doas: it fails if anything of the live session (live user, its home, `live-user` script or runlevel link, autologin) reached the install, then turns on GDM autologin for `tester`, restarts gdm and runs `test/features.sh` as `tester` with the environment of the user's `gnome-shell`, then `test/apparmor.sh` as root. `test/apparmor.sh` checks that every system daemon Fedora's SELinux targeted policy gives a domain of its own (named in each test) runs under an AppArmor profile in enforce mode, starting D-Bus-activated ones first. sshd is installed but not enabled, so it starts it, logs in through it as a throwaway user with a key (checking sshd-session and sshd-auth before authentication, the session after, and sftp), then stops it, deleting the host keys the start made, and deletes the user; the profiles are in `apparmor.d/` (see below). `test.sh` prints its own results in `test/features.sh`'s format, then the counts of all the tests together. Last, it logs `tester` out through gnome-session and fails unless the session ends and GDM's login screen comes back (a new `gnome-shell` as `gdm` that stays up, answers on D-Bus, runs the `gnome-shell-compat` helper and is seat0's active elogind session); this has to live in `test.sh`, not `test/features.sh`, because it ends the session the tests run in. After that, its last test fails on any AppArmor denial in the installed system's kernel log, so it covers everything the tests did. No setup happens between install and test: the ISO itself must make every test pass. The guest gets the repo files as a tar archive on `/dev/vdb`, and each command's exit status comes back as an `@@RC=n@@` marker on the console.

`shellcheck build-alpine-gnome-iso.sh genapkovl-gnomelive.sh` is useful, but the scripts the generator writes out through heredocs are not checked by it.

CI (`.github/workflows/build-iso.yml`) runs the script with `CONTAINER=docker` on pushes/PRs that touch the script, the generator, `apparmor.d/`, `ci/`, `test/` or the workflow, once per `TARGET` (a matrix of `iso` and `rpi`). Each job uploads its image plus `SHA256SUMS` as an artifact; the `iso` job then runs `ci/vm-test.sh` and fails unless every OS feature test passes (the console logs are uploaded on failure). The `rpi` image is only built: QEMU can't run GNOME on an emulated Pi. A separate `release` job publishes both images as a GitHub release on `v*` tags, only after both build jobs pass. It frees runner disk space first because mkimage needs several GB.

## How the script is structured

`TARGET` sets `ARCH` (`x86_64` or `aarch64`) at the top of the script. The container always runs the host's architecture: mkimage cross-builds for `--arch "$ARCH"` (apk fetches and `update-kernel` don't run target code), so nothing may execute target binaries during the build.

The same file runs in three phases, selected by its first argument:

1. **`host_main`** (no argument): picks the container runtime, resolves `ALPINE_BRANCH` from the mirror's `latest-releases.yaml`, and re-runs itself in `alpine:<release>`, mounting itself at `/build.sh`, `genapkovl-gnomelive.sh` and `apparmor.d/` (from the script's directory) at `/genapkovl-gnomelive.sh` and `/apparmor.d`, and `$OUTDIR` at `/out`. Settings reach the container only through the explicit `-e` flags, so a new setting must be added there too. `--security-opt label=disable` is deliberate (not `:Z`) so libvirt can still open the ISO on SELinux hosts.
2. **`container_main`** (`--in-container`, as root): installs the build tools, creates the unprivileged `build` user and an abuild signing key (installed into `/etc/apk/keys` by hand, because `abuild-keygen -i` would call doas/sudo), then runs phase 3 as `build`. mkimage must not run as root: apk 3 rejects `--no-chown` as root.
3. **`builder_main`** (`--as-builder`): sparse-clones `aports/scripts` at `<release>-stable`, resolves the package list `setup-desktop gnome` would install (`apk info --depends gnome gnome-apps-core`, in an apk root for `$ARCH`, plus the wayland-base and udev packages) and adds `$features`, the packages for what `test/features.sh` checks (some only exist on one architecture, e.g. the Intel VA-API drivers; `iproute2-minimal` is for its IPv6 reverse path filter test, which needs `ip netns`). It writes the profile into `aports/scripts/` and puts the apkovl generator there with what it reads: `genapkovl-gnomelive.conf` (the build settings `LIVE_USER`, `LIVE_PASSWORD`, `AUTOLOGIN`, `KERNEL_OPTS` (kernel arguments) and `WORLD`, the package list, as `sh` assignments), Flathub's downloaded `flathub.flatpakrepo` and the `apparmor.d/` directory. Then it runs `mkimage.sh --profile gnomelive`:
   - `mkimg.gnomelive.sh`: a profile that extends `profile_standard` (for `rpi`: `profile_rpiimg`, keeping `hostname="rpi"`, which mkimage's `section_rpi_config` requires, plus a section that puts `usercfg.txt`, turning on the vc4 KMS overlay, on the boot partition), adds the package list to the image's on-disc apk repo and `KERNEL_OPTS` (AppArmor's `lsm=` and `cryptdiscards=yes`, so an encrypted root passes the SSD fstrim's discards; for `rpi` also `nvme.max_host_mem_size_mb=64`, raising the 32 MB NVMe host memory buffer cap the Pi firmware's device tree sets, and `cgroup_enable=memory`, undoing the `cgroup_disable=memory` it also sets, and `console=tty1`, so `/dev/console`, where the initramfs asks for an encrypted root's passphrase, is the screen rather than the device tree's debug UART) to the kernel command line.
   - `genapkovl-gnomelive.sh` (a source file in the repo, copied in): builds the apkovl (the `lbu` overlay format) holding `/etc/apk/world`, the GDM `custom.conf` (autologin), the desktop features' config files (profile.d, locale, NetworkManager, nftables, zram, coredump handler, Flathub remote, sshd's sftp subsystem (the external `sftp-server`, so sshd's profile need not reach the user's files), the autostart helper that registers the session with GDM and answers gnome-session's end-of-session queries for GNOME Shell, also listed in GDM's greeter autostart directory so the login screen registers too, ...), the AppArmor profiles with the conf.d files, `/etc/inittab` and `/usr/local/libexec` helpers that start some daemons under them, OpenRC runlevel symlinks, a `live-user` init script, `setup-alpine`, `lbu` and `adduser` wrappers in `/usr/local/sbin`, and an "Install Alpine Linux" launcher in `/usr/local/share/applications` that runs the `setup-alpine` wrapper in GNOME Console.

Everything the desktop features need on an installed system must be under `/etc` (or listed in `/etc/apk/protected_paths.d/lbu.list`, as `/usr/local/libexec` and the greeter's autostart file are), because `setup-disk` only copies what `lbu package` includes.

At boot the initramfs unpacks the apkovl, installs `/etc/apk/world` from the disc into the tmpfs root, and OpenRC starts the services.

### Editing the generated files

Most changes happen in `genapkovl-gnomelive.sh`, which writes each file of the apkovl with a heredoc:

- Use a quoted `<<'EOF'` heredoc for a file with no build settings in it, so it is written out as is.
- A file that needs a build setting (the `live-user` init script, the `setup-alpine` and `lbu` wrappers, `/etc/apk/world`, GDM's `custom.conf`) uses an unquoted `<<EOF`: `$LIVE_USER`, `$KERNEL_OPTS` etc. are filled in when the generator runs, and the generated script's own variables need `\$` (and a literal backslash `\\`).
- A new build setting has to be added to the `genapkovl-gnomelive.conf` that `builder_main` writes, quoted with `shquote`.
- The mkimage profile is still a `<<-EOF` heredoc in `builder_main`; it strips leading **tabs**, so indent it with tabs only.
- Runlevels mirror the standard ISO's, changed the way `setup-desktop gnome` changes them: udev in place of mdev/hwdrivers, plus `cgroups`, `dbus`, `live-user` and `gdm` in default. The desktop features add `zram-init` to boot, `apparmor` to sysinit (its conf.d orders it before udev, so udevd starts confined), and their daemons (NetworkManager, chronyd, cupsd, ...) to default.
- The `setup-alpine` wrapper exists so installing from inside the live desktop works. It puts temporary shims first in `PATH`: `openrc` with `--no-stop` (so gdm and dbus are not killed); `rc-service`, which skips `networking stop`/`start` and turns `hostname restart` into a plain `hostname` call (both would stop dependents such as chronyd and avahi and restart them in the background, where they deadlock on OpenRC's service locks with the next step's udev stop); `setup-devd`, which skips the `-C mdev` bootstrap (udev is already running); and no-op `setup-interfaces`/`setup-dns` (NetworkManager manages the network; ifupdown only has `lo`). The `openrc` and `rc-service` shims run OpenRC under `setsid -w`, so Ctrl-C cannot kill a service transition halfway and leave its lock and state behind. It defaults `DEVDOPTS=udev`, `APKREPOSOPTS=-c` (community enabled), `MIRRORS` (which `setup-apkrepos` picks from) to the `https://` URLs in `mirrors.alpinelinux.org/mirrors.json`, falling back to the CDN, since its default `mirrors.txt` only lists `http://` ones, `USEROPTS` with the `plugdev` and `lpadmin` groups, `KERNELOPTS` with `KERNEL_OPTS` (AppArmor's `lsm=`, `cryptdiscards=yes`, and on the Pi the NVMe cap, the memory cgroup controller and `console=tty1`), `SSHDOPTS=none` (no SSH server) and `NTPOPTS=none` (setup-ntp's default, busybox ntpd, would run next to chronyd, which the install already has from the live runlevels), and passes `-e` so no root password is asked for. An answer file passed with `-f` still overrides those defaults (but not `-e`).
- `setup-alpine` sources `/etc/profile` part way through, which resets `PATH` and drops the temporary shims. So shims needed after that point live permanently in `/usr/local/sbin`, which `/etc/profile` puts first. `lbu`: `setup-disk` copies the live `/etc` to the target with `lbu package -`, and the shim filters that archive to drop the live user (passwd/shadow/group), its home directory (`setup-alpine` runs `lbu add` on every `/home/*`), the `live-user` init script and runlevel link, and GDM autologin; if the copy's `wheel` group has a member, it also locks root's password (`!`). It also starts the serial-console getty the initramfs added to `inittab` through `apparmor-exec`. On the Pi it adds `boot/usercfg.txt` (from `/usr/local/share/gnomelive`, which only the Pi's apkovl has): `setup-disk` unpacks the archive into the target with its boot partition mounted on `/boot`. `adduser`: gives users created by `setup-user` bash as their login shell and a mode 0700 home directory (`/etc/default/useradd` and `HOME_MODE` in `/etc/login.defs` do the same for shadow's `useradd`, which GNOME Settings uses).

### AppArmor profiles

`apparmor.d/` holds one profile per daemon that `test/apparmor.sh` checks (Avahi's and dnsmasq's come from Alpine's `apparmor-profiles`; `apparmor.d/local/usr.sbin.dnsmasq` adds what NetworkManager's `dns=dnsmasq` instance needs through that profile's `local/` include), all in enforce mode; the generator copies them, `local/` included, into the apkovl's `/etc/apparmor.d`. Each attaches by the daemon's path, except where a path can't single the daemon out: busybox applets (`busybox-syslogd`, `busybox-crond`, `busybox-acpid`, `busybox-getty`) and the system bus (`dbus-system`; the same `dbus-daemon` runs every session bus). Those are started under their profile by name through `/usr/local/libexec/apparmor-exec` (which runs them unconfined if the profile isn't loaded): the services' conf.d files source `/usr/local/libexec/apparmor-start.sh`, which replaces OpenRC's default `start` (so it only works while the init script doesn't define its own), and the apkovl's `/etc/inittab` wraps the gettys. The serial console getty the initramfs appends to inittab is wrapped by the `lbu` shim, so only on installed systems. Helpers a daemon runs either stay in its profile (`ix`), or run unconfined (`Ux`) when they are the user's session, a login or service control (sessions from `gdm-session-worker`, jobs from crond, poweroff from elogind, D-Bus activation through `dbus-daemon-launch-helper`, after which each service attaches to its own profile). Every profile accepts signals from `peer=busybox`: root's shells (and `rc-service`, `kill`, `killprocs` run from them) carry the label of Alpine's unconfined-mode `busybox` profile, not `unconfined`, which `abstractions/base` already lets in. Alpine's `dbus-daemon` has no AppArmor support and the kernel doesn't mediate Unix sockets, so the profiles have no `dbus` or `unix` rules.

To work out what a daemon needs, load its profile with `flags=(complain)`, exercise it, and collect the `apparmor="ALLOWED"` lines from `dmesg` (boot with `audit_backlog_limit=` raised and set `kernel.printk_ratelimit=0`, or messages get dropped); then check for `apparmor="DENIED"` in enforce mode. `apparmor_parser -QT -K <file>` in an Alpine container checks a profile's syntax.
