# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Bash script, `build-alpine-gnome-iso.sh` (with its apkovl generator `genapkovl-gnomelive.sh`, the `cervino-desktop` package's `cervino-desktop/APKBUILD` and the AppArmor profiles in `apparmor.d/`), that builds a bootable x86_64 Alpine Linux live ISO that boots straight into GNOME, or with `TARGET=rpi` an aarch64 Raspberry Pi SD card image (`.img.gz`) of the same system. It reproduces what `setup-desktop gnome` would install and enable, on top of Alpine's "standard" ISO (or its `rpiimg` image). `README.md` documents the user-facing behaviour and the environment variables (`TARGET`, `ALPINE_BRANCH`, `OUTDIR`, `LIVE_USER`, `LIVE_PASSWORD`, `AUTOLOGIN`, `BROWSER`, `CONTAINER`, `MIRROR`, `SIGNING_KEY`, `APK_REPO`). Keep the README table, the script's header comment and the workflow in sync when you add or change a setting.

## Build and test

There are no unit tests or linters. A change is checked by building the ISO and booting it:

```sh
./build-alpine-gnome-iso.sh                       # needs podman or docker, curl, network
ALPINE_BRANCH=v3.24 AUTOLOGIN=0 ./build-alpine-gnome-iso.sh
qemu-system-x86_64 -enable-kvm -m 8G -cdrom out/*.iso   # live system runs from RAM: ~6 GB+
ci/vm-test.sh out/*.iso                             # the end-to-end test CI runs
INSTALL_MODE=sys ci/vm-test.sh out/*.iso            # the same with a sys install
```

`ci/vm-test.sh` drives QEMU/KVM boots over the serial console, keeping the logs in `$WORKDIR` (default `./vm-test`). First it boots the ISO's kernel directly, with the `APPEND` line from the ISO's `syslinux.cfg` plus `console=ttyS0` (the ISO's boot loaders have no serial console), and installs to `/dev/vda` with `ci/guest/install.sh`, which first checks that reinstalling `apparmor-profiles` from the disc fires the package's trigger (the kernel's AppArmor policy revision changes), then runs an answer file (`-m $INSTALL_MODE`: `atomic`, the default, or `sys`; `install.sh` and `test.sh` take it as their argument) through the ISO's `setup-alpine` wrapper and then fails if the live system's kernel log has any AppArmor denials (`ci/guest/apparmor-denials.sh`). Then it boots the disk, logs in as `tester` (root is locked there; after installing, `install.sh` mounts the disk, clears tester's password, which the install leaves locked, and adds a `permit nopass tester` doas rule) and runs `ci/guest/test.sh` through doas: it fails if anything of the live session (live user, its home, `live-user` script or runlevel link, autologin) reached the install, then turns on GDM autologin for `tester`, restarts gdm and runs `test/features.sh` as `tester` with the environment of the user's `gnome-shell`, then `test/apparmor.sh` as root, then checks that the package's "Update Alpine Linux" launcher shows in the app grid (GLib's `Gio.DesktopAppInfo` in tester's session) and what it runs is installed, and that the system is read-only (atomic) or writable (sys). `test/apparmor.sh` checks that every system daemon Fedora's SELinux targeted policy gives a domain of its own (named in each test) runs under an AppArmor profile in enforce mode, starting D-Bus-activated ones first. sshd is installed but not enabled, so it starts it, logs in through it as a throwaway user with a key (checking sshd-session and sshd-auth before authentication, the session after, and sftp), then stops it, deleting the host keys the start made, and deletes the user; the profiles are in `apparmor.d/` (see below). `test.sh` prints its own results in `test/features.sh`'s format, then the counts of all the tests together. Then it puts the memory under pressure: `ci/guest/memory-hog.js`, run with gjs in tester's session, takes memory 64 MiB at a time, every 200 ms (pages of one repeated byte, which zram stores without compressing, so swap fills as fast as RAM and the VM doesn't thrash; unpaced, swap filled so fast that earlyoom, which checks at most once a second, missed the window about half the time), and the test fails unless earlyoom kills it, and only it, before the kernel's OOM killer acts, with GNOME Shell still running; this runs before the logout, which needs the session. Last, it logs `tester` out through gnome-session and fails unless the session ends and GDM's login screen comes back (a new `gnome-shell` as `gdm` that stays up, answers on D-Bus, runs the `gnome-shell-compat` helper and is seat0's active elogind session); this has to live in `test.sh`, not `test/features.sh`, because it ends the session the tests run in. After that, its last test fails on any AppArmor denial in the installed system's kernel log, so it covers everything the tests did. Then, on an atomic install only, three more boots run `ci/guest/upgrade.sh stage`, `check` and `rollback`: `apk add` (through the wrapper, so `update-alpine add`) of a small package not installed (`figlet`, ...) must stage a new version and leave the running one alone, the shutdown must switch to it with `/etc` changes made after staging (a file written, one deleted), Limine's menu must start it first and keep the old one, and `update-alpine rollback` must make a new copy of the old version the default, which `update-alpine list` must show as running and next to start, and `update-alpine delete` must remove the updated version from the volume and the boot partition but refuse the running one; notes between the boots are kept in `/var/lib/cervino-ci`. No setup happens between install and test: the ISO itself must make every test pass. The guest gets the repo files as a tar archive on `/dev/vdb`, and each command's exit status comes back as an `@@RC=n@@` marker on the console.

`ci/update-test.sh out/repo` tests the package's `update-alpine` (taken out of the built `.apk` with `tar`) in plain `alpine` containers, in seconds: on the package's release it must upgrade the packages and check for a newer release; on the release before, it installs a stand-in `cervino-desktop` (only a `cervino.list` naming its own repo; made with `apk mkpkg`/`apk mkndx`, signed with a throwaway key, served by busybox-extras' `httpd` on `127.0.0.1:8080`), and `update-alpine` must offer nothing and change nothing while that repo has no packages for the newer release; once it has, offer it, change nothing when that is turned down, and when accepted leave `/etc/alpine-release`, `/etc/apk/repositories` and `cervino.list` on it, with the newer release's stand-in installed, no `cervino.list.apk-new` and nothing left to upgrade. These run in containers rather than the VM because they change the system and the VM's release is always the latest.

`shellcheck build-alpine-gnome-iso.sh genapkovl-gnomelive.sh` is useful, but the scripts the generator and the APKBUILD write out through heredocs are not checked by it.

CI (`.github/workflows/build-iso.yml`) runs the script with `CONTAINER=docker` on pushes/PRs that touch the script, the generator, `cervino-desktop/`, `apparmor.d/`, `ci/`, `test/` or the workflow, once per `TARGET` (a matrix of `iso` and `rpi`). Each job uploads its image plus `SHA256SUMS` as an artifact; the `iso` job then runs `ci/update-test.sh`. The `vm-test` job (after both builds) downloads the ISO and runs `ci/vm-test.sh` once per `INSTALL_MODE` (a matrix of `atomic` and `sys`, on separate runners, since a runner's 16 GB can't hold two 8 GB VMs), failing unless every OS feature test passes (the console logs are uploaded as `vm-test-logs-<mode>` on failure). The `rpi` image is only built: QEMU can't run GNOME on an emulated Pi. A separate `release` job publishes both images as a GitHub release on `v*` tags, only after both build jobs and both VM tests pass. On those tags the build jobs also sign with the `APK_SIGNING_KEY` secret, written to `$RUNNER_TEMP/cervino.rsa` (apk knows a key by its file name, so it stays `cervino.rsa` in every job). The secret belongs to the `release` environment, whose deployment rule admits only `v*` tags, so branch runs can't read it: the `repo` job always enters it, the build job only on tags (its `environment:` expression is empty otherwise). The build jobs also set `APK_REPO` to the repository's GitHub Pages URL, and each uploads its `out/repo` (the package as `<branch>/<arch>/cervino-desktop-*.apk`) as `cervino-repo-<target>`. The `repo` job (also after the VM tests) then runs `ci/publish-repo.sh` in an `alpine:<branch>` container per branch (so the index is in a format that branch's apk reads) on a worktree of the `gh-pages` branch (an orphan branch holding only the published repo, created on the first release, written only by this job, one run at a time): it adds the packages, keeps the newest five per arch, indexes each arch with `--rewrite-arch`, signs the index and pushes. GitHub Pages serves that branch; Pages must be set to it in the repository settings. It frees runner disk space first because mkimage needs several GB.

## How the script is structured

`TARGET` sets `ARCH` (`x86_64` or `aarch64`) at the top of the script. The container always runs the host's architecture: mkimage cross-builds for `--arch "$ARCH"` (apk fetches and `update-kernel` don't run target code), so nothing may execute target binaries during the build.

The same file runs in three phases, selected by its first argument:

1. **`host_main`** (no argument): picks the container runtime, resolves `ALPINE_BRANCH` from the mirror's `latest-releases.yaml`, and re-runs itself in `alpine:<release>`, mounting itself at `/build.sh`, `genapkovl-gnomelive.sh`, `cervino-desktop/` and `apparmor.d/` (from the script's directory) at `/genapkovl-gnomelive.sh`, `/cervino-desktop` and `/apparmor.d`, and `$OUTDIR` at `/out`. It also passes `PKGVER`, the package's version: the last commit's time (`YYYYMMDD.HHMMSS`, UTC), or the build time outside git, so each commit's package upgrades the last. Settings reach the container only through the explicit `-e` flags, so a new setting must be added there too. `--security-opt label=disable` is deliberate (not `:Z`) so libvirt can still open the ISO on SELinux hosts.
2. **`container_main`** (`--in-container`, as root): installs the build tools, creates the unprivileged `build` user and its abuild signing key: `SIGNING_KEY`, mounted at `/signing-key` with its file name in `SIGNING_KEY_NAME` (the public key is derived with openssl as `<name>.pub`), or else a new one from `abuild-keygen` (installed into `/etc/apk/keys` by hand, because `abuild-keygen -i` would call doas/sudo), then runs phase 3 as `build`, and copies the image and the package (`/work/pkgout`, as `/out/repo/<branch>/<arch>/`) to `/out`. mkimage must not run as root: apk 3 rejects `--no-chown` as root.
3. **`builder_main`** (`--as-builder`): sparse-clones `aports/scripts` at `<release>-stable`, resolves the package list `setup-desktop gnome` would install (`apk info --depends gnome gnome-apps-core`, in an apk root for `$ARCH`, plus the wayland-base and udev packages) and adds `$features`, the packages for what `test/features.sh` checks (some only exist on one architecture, e.g. the Intel VA-API drivers; `iproute2-minimal` is for its IPv6 reverse path filter test, which needs `ip netns`). `/etc/apk/world` is what `setup-desktop gnome` would put there plus `cervino-desktop`, which depends on `$features`: a feature added later reaches installed systems with the package, while GNOME's apps stay removable from world. It builds the package with `abuild -d` in `/work/cervino/cervino-desktop`, from a copy of `cervino-desktop/` with `cervino-desktop.conf` (`PKGVER`, `DEPENDS`, the features, `PUBKEY`, the file name of the signing key's public key, copied next to it, and `REPO`, `$APK_REPO/$ALPINE_BRANCH` or empty, as `sh` assignments), Flathub's downloaded `flathub.flatpakrepo` and the `apparmor.d/` directory next to the APKBUILD, signed with the build's key (which mkimage puts in the image, so the live system and installs trust it), and indexes it in a repo of its own, `/work/pkgrepo/$ARCH`, as a package for `$ARCH` (`apk index --rewrite-arch`: abuild files a noarch package under the container's architecture, and apk 3 fetches a package from the directory of the arch its index records), which mkimage gets as a third `--repository`. It writes the profile into `aports/scripts/` and puts the apkovl generator there with what it reads: `genapkovl-gnomelive.conf` (the build settings `TARGET`, `LIVE_USER`, `LIVE_PASSWORD`, `AUTOLOGIN`, `KERNEL_OPTS` (kernel arguments) and `WORLD`, the package list, as `sh` assignments). Then it runs `mkimage.sh --profile gnomelive`:
   - `mkimg.gnomelive.sh`: a profile that extends `profile_standard` (for `rpi`: `profile_rpiimg`, keeping `hostname="rpi"`, which mkimage's `section_rpi_config` requires, plus a section that puts `usercfg.txt`, turning on the vc4 KMS overlay, on the boot partition), adds the package list to the image's on-disc apk repo and `KERNEL_OPTS` (AppArmor's `lsm=`, `cryptdiscards=yes`, so an encrypted root passes the SSD fstrim's discards, and `sysctl.kernel.printk_ratelimit=0 audit_backlog_limit=8192 log_buf_len=4M`, so with no auditd the kernel log keeps every AppArmor message, which the denial checks rely on; for `rpi` also `nvme.max_host_mem_size_mb=64`, raising the 32 MB NVMe host memory buffer cap the Pi firmware's device tree sets, and `cgroup_enable=memory`, undoing the `cgroup_disable=memory` it also sets, and `console=tty1`, so `/dev/console`, where the initramfs asks for an encrypted root's passphrase, is the screen rather than the device tree's debug UART) to the kernel command line.
   - `genapkovl-gnomelive.sh` (a source file in the repo, copied in): builds the apkovl (the `lbu` overlay format) holding what only the live system has: `/etc/apk/world`, the GDM `custom.conf` (autologin), OpenRC runlevel symlinks, a `live-user` init script, `setup-alpine`, `lbu`, `adduser` and `setup-disk` wrappers in `/usr/local/sbin`, and an "Install Alpine Linux" launcher in `/usr/local/share/applications` that runs the `setup-alpine` wrapper in GNOME Console (plus a `Hidden=true` entry there that hides the package's "Update Alpine Linux" launcher).

`cervino-desktop/APKBUILD` holds the desktop features' config files (profile.d, locale, NetworkManager, nftables, zram, earlyoom, coredump handler, cron/anacron, Flathub remote, sshd's sftp subsystem (the external `sftp-server`, so sshd's profile need not reach the user's files), the "Update Alpine Linux" launcher and its `/usr/sbin/update-alpine` (package upgrade, then an offered release upgrade), the autostart helper that registers the session with GDM and answers gnome-session's end-of-session queries for GNOME Shell, also listed in GDM's greeter autostart directory so the login screen registers too, ...), the AppArmor profiles with the conf.d files, `/etc/inittab` and the `/usr/libexec/cervino` helpers that start some daemons under them. abuild rejects files under `/usr/local`. The package has `options="!tracedeps"`: abuild would otherwise make it provide `cmd:apk` for the apk wrapper, which conflicts with `apk-tools`; then the live system's boot-time install fails (quietly: the boot goes on with an almost empty root), so `builder_main` checks that the world installs with the built package (`apk add --simulate`) and stops the build if not. Files other packages own (alpine-baselayout's `inittab` and root crontab, shadow's `login.defs`, some daemons' conf.d files) are taken over with `replaces=`, which also keeps ours when those packages are upgraded; a new one needs its owner (`apk info --who-owns` in an Alpine container) added there, or installing fails with a file conflict. Like any package's, a file in `/etc` the user changed is kept on upgrade, with ours written next to it as `.apk-new`, so settings belong in drop-in files where the daemon reads them. `cervino-desktop.post-install` adds the features' services to their runlevels (the same as the apkovl's; their `-openrc` packages are dependencies so their init scripts are there first); it runs only on install, so a service the user disabled stays off on upgrades. `cervino-desktop.trigger` runs `rc-service apparmor reload` when any package changes `/etc/apparmor.d`, only where the apparmor service is started (not in the initramfs or `setup-disk`'s chroot), and `/usr/libexec/cervino/update-boot` when one changes `/boot` or `/usr/share/limine`.

Atomic installs (below) are run by `/usr/libexec/cervino/atomic.sh`, which `update-boot`, `update-alpine` and `atomic-finalize` source. `atomic_detect` is true only on an atomic install's running version: `/etc/kernel/cmdline` exists, `/` is a `roots/<id>` subvolume, and `btrfs inspect-internal rootid /` matches the mount's `subvolid`, so in `update-alpine`'s chroot of a new version (where the kernel hook and the package trigger also run) they all do nothing. The volume's top level (mounted on `/run/cervino-volume.*`, as `/tmp` is gone at shutdown) holds `roots/<id>` (UTC `YYYYMMDDHHMMSS`; read-only, with a writable nested `etc` subvolume), and while an update is staged `staged` ("NEWID FROMID merge") and `etc-base`, a read-only snapshot of the running `/etc` taken when staging. `update-boot` copies each complete version's (read-only, not staged) kernel, initramfs and microcode to `/boot/efi/cervino/<id>/`, writes `/boot/efi/limine/limine.conf` (newest first, older ones under "Earlier versions", each entry's command line its `/etc/kernel/cmdline` plus `rootflags=subvol=/roots/<id>`), and copies Limine's UEFI and BIOS files, rerunning `limine bios-install` when the latter change. Atomic installs turn mkinitfs's trigger off (`disable_trigger=yes`); the package's `/etc/kernel-hooks.d/50-cervino-boot` (run by `kernel-hooks`) builds the initramfs and then runs `update-boot`. `update-alpine` on an atomic install (under `flock /run/cervino-update.lock`) snapshots the staged version if there is one, else the running one (its `etc` from `etc-base`), binds `/proc`, `/sys`, `/dev` and `/var` into it with tmpfs `/run` and `/tmp`, and runs the same apk steps as on other systems in a chroot of it (`$R` prefixes the files it edits, `run` the commands), then, if the installed database, world or repositories changed, makes it read-only and stages it; `add`/`del` run `apk add`/`del` instead, and `rollback` stages a copy of the newest complete version older than the running one with no merge. `list` prints each version (id, date, running, staged, incomplete, next to start); `delete ID...` (under the same lock) deletes versions, never the running one (the staged one with `atomic_unstage`), then runs `update-boot`. The `cervino-atomic` service (shutdown runlevel, added by `post-install`) runs `atomic-finalize`: unless the staged version was made from another one (then it is deleted), it lists what changed in `/etc` since `etc-base` with `rsync -n -i -c --delete`, copies that into the new `etc` (an update's change to a file changed meanwhile is kept as `.apk-new`), deletes `etc-base` and `staged`, deletes all but the newest four complete versions (and the running one), and runs `update-boot`, which mounts `/boot/efi` itself since `localmount` has stopped. Elsewhere (sys installs, the containers of `ci/update-test.sh`, which have no `atomic.sh`) `update-alpine` changes the running system as before. The package's `/usr/sbin/apk`, ahead of `/sbin/apk` in `/etc/profile`'s and doas's `PATH` (Alpine has no `/usr` merge yet; with one they would be the same file), is a wrapper: on an atomic install's running system it hands `apk add`/`del` (plain package names, harmless options only) to `update-alpine add`/`del` and `apk upgrade` to `update-alpine`, and turns down `fix` and other options; everything else, `--simulate`, `--root`, and any other system (including `update-alpine`'s chroot) gets `/sbin/apk` unchanged.

`setup-disk` installs `/etc/apk/world` (so the package) on the target from the live system's repositories, the disc's included, and copies what `lbu package` includes (files under `/etc` that differ from their package's) over it; the apkovl's live-only files under `/usr/local` don't reach installs. The apkovl's `setup-disk` shim asks whether to install `atomic` (the default) or `sys` (`-m atomic`/`-m sys` in answer files); `sys` (when chosen at its question, after it has asked for the disk and whether to encrypt, as `-m sys [-e] <disk>`, so Alpine's doesn't ask its own sys/data/crypt/lvm question), and options it doesn't handle (`-m data`, `-L`, `-r`, several disks, a mount point, ...), go to Alpine's `setup-disk`. Like Alpine's, it can install to the disk the live system started from after `copy-modloop` (the Pi's SD card). For an atomic install on a PC it does the partitioning itself: GPT with a 1 MiB BIOS boot partition, a 1 GiB FAT boot partition (mounted on `/boot/efi`), swap sized as Alpine's `setup-disk` sizes it (needed: without it the earlyoom test fails, the kernel's OOM killer acting first; on an encrypted disk `dmcrypt` in boot opens it with a random key) and btrfs, on LUKS2 (`cryptdm=root`) if asked to encrypt, holding `@var`, `@home` and `roots/<id>` (UTC `YYYYMMDDHHMMSS`) with a nested `etc` subvolume; it mounts those on `/mnt` and runs Alpine's `setup-disk` on that mounted root with `BOOTLOADER=none`, then rewrites fstab, writes `/etc/kernel/cmdline`, removes `gnome-software-plugin-apk2` (in world from `gnome-apps-core`) and the `apk-polkit-server` runlevel link, as apk cannot write to the system, moves `/root` to `/var/roothome` (a symlink), makes the root subvolume read-only and runs `update-boot`, which installs Limine (both UEFI and BIOS). On a Pi (`/proc/device-tree/model`) the table is MBR: the firmware's FAT partition first (mounted on `/boot/firmware`), swap only with `-s` (Alpine's default there), then btrfs; it copies `usercfg.txt` there. `update-boot` tells a Pi by `start4.elf`/`bootcode.bin` in the root's `/boot` (from `raspberrypi-bootloader`, in the Pi's features with the atomic tools): it copies each version's kernel (`vmlinuz-rpi*` as Alpine's `config.txt` picks it), initramfs, `*.dtb` and `overlays/` once into `cervino/<id>.new`, renamed to `cervino/<id>/`, adds `overlays/README` (the firmware ignores `os_prefix` for overlays without one, and Alpine's kernel ships none), writes its `cmdline.txt`, copies the firmware files from the newest version, and writes `config.txt` with `os_prefix=cervino/<newest>/` (earlier versions as comments). The firmware has no menu; the Pi path has not been run on hardware.

At boot the initramfs unpacks the apkovl, installs `/etc/apk/world` from the disc into the tmpfs root, and OpenRC starts the services.

### Editing the generated files

Most changes happen in `cervino-desktop/APKBUILD` (the desktop features) or `genapkovl-gnomelive.sh` (the live system), which write each file with a heredoc:

- Use a quoted `<<'EOF'` heredoc for a file with no build settings in it, so it is written out as is. The APKBUILD's files have none (build settings are the live system's), except the signing key in `/etc/apk/keys`, so a later package can bring a new one, and with `APK_REPO`, `/etc/apk/repositories.d/cervino.list` (apk 3 reads those lists besides `/etc/apk/repositories`, which stays the user's), from `cervino-desktop.conf`.
- A file that needs a build setting (the `live-user` init script, the `setup-alpine` and `lbu` wrappers, `/etc/apk/world`, GDM's `custom.conf`) uses an unquoted `<<EOF`: `$LIVE_USER`, `$KERNEL_OPTS` etc. are filled in when the generator runs, and the generated script's own variables need `\$` (and a literal backslash `\\`).
- A new build setting has to be added to the `genapkovl-gnomelive.conf` that `builder_main` writes, quoted with `shquote`.
- The mkimage profile is still a `<<-EOF` heredoc in `builder_main`; it strips leading **tabs**, so indent it with tabs only.
- Runlevels mirror the standard ISO's, changed the way `setup-desktop gnome` changes them: udev in place of mdev/hwdrivers, plus `cgroups`, `dbus`, `live-user` and `gdm` in default. The apkovl also holds the desktop features' runlevels: `zram-init` in boot, `apparmor` in sysinit (its conf.d orders it before udev, so udevd starts confined), and their daemons (NetworkManager, chronyd, earlyoom, cupsd, ...) to default.
- The `setup-alpine` wrapper exists so installing from inside the live desktop works. It puts temporary shims first in `PATH`: `openrc` with `--no-stop` (so gdm and dbus are not killed); `rc-service`, which skips `networking stop`/`start` and turns `hostname restart` into a plain `hostname` call (both would stop dependents such as chronyd and avahi and restart them in the background, where they deadlock on OpenRC's service locks with the next step's udev stop); `setup-devd`, which skips the `-C mdev` bootstrap (udev is already running); `rc-update`, which turns `add crond` into `add cronie` (busybox crond never runs a daily/weekly/monthly job the machine was off for; the apkovl's root crontab keeps only the 15min and hourly runs, and `/etc/cron.d/anacron` runs anacron at boot and hourly for `/etc/anacrontab`'s) and skips `add acpid` (busybox acpid's only handler powers off on the power button at once, going around elogind and GNOME's power button setting; its profile stays for anyone who enables it, but no test checks it, as it never runs in the VM); and no-op `setup-interfaces`/`setup-dns` (NetworkManager manages the network; ifupdown only has `lo`). The `openrc` and `rc-service` shims run OpenRC under `setsid -w`, so Ctrl-C cannot kill a service transition halfway and leave its lock and state behind. It defaults `DEVDOPTS=udev`, `APKREPOSOPTS=-c` (community enabled), `MIRRORS` (which `setup-apkrepos` picks from) to the `https://` URLs in `mirrors.alpinelinux.org/mirrors.json`, falling back to the CDN, since its default `mirrors.txt` only lists `http://` ones, `USEROPTS` with the `plugdev` and `lpadmin` groups, `KERNELOPTS` with `KERNEL_OPTS` (AppArmor's `lsm=`, `cryptdiscards=yes`, the kernel log limits, and on the Pi the NVMe cap, the memory cgroup controller and `console=tty1`), `SSHDOPTS=none` (no SSH server) and `NTPOPTS=none` (setup-ntp's default, busybox ntpd, would run next to chronyd, which the install already has from the live runlevels), and passes `-e` so no root password is asked for. An answer file passed with `-f` still overrides those defaults (but not `-e`).
- `setup-alpine` sources `/etc/profile` part way through, which resets `PATH` and drops the temporary shims. So shims needed after that point live permanently in `/usr/local/sbin`, which `/etc/profile` puts first: `setup-disk` (see above) and `lbu`, `adduser`. `lbu`: `setup-disk` copies the live `/etc` to the target with `lbu package -`, and the shim filters that archive to drop the live user (passwd/shadow/group), its home directory (`setup-alpine` runs `lbu add` on every `/home/*`), the `live-user` init script and runlevel link, and GDM autologin; if the copy's `wheel` group has a member, it also locks root's password (`!`). It also starts the serial-console getty the initramfs added to `inittab` through `apparmor-exec`. On the Pi it adds `boot/usercfg.txt` (from `/usr/local/share/gnomelive`, which only the Pi's apkovl has): `setup-disk` unpacks the archive into the target with its boot partition mounted on `/boot`. `adduser`: gives users created by `setup-user` bash as their login shell and a mode 0700 home directory (`/etc/default/useradd` and `HOME_MODE` in `/etc/login.defs` do the same for shadow's `useradd`, which GNOME Settings uses).

### AppArmor profiles

`apparmor.d/` holds one profile per daemon that `test/apparmor.sh` checks (but `busybox-acpid`, for acpid, which installs leave off) (Avahi's and dnsmasq's come from Alpine's `apparmor-profiles`; `apparmor.d/local/usr.sbin.dnsmasq` adds what NetworkManager's `dns=dnsmasq` instance needs through that profile's `local/` include), all in enforce mode; the APKBUILD copies them, `local/` included, into the package's `/etc/apparmor.d`. Each attaches by the daemon's path, except where a path can't single the daemon out: busybox applets (`busybox-syslogd`, `busybox-acpid`, `busybox-getty`) and the system bus (`dbus-system`; the same `dbus-daemon` runs every session bus). Those are started under their profile by name through `/usr/libexec/cervino/apparmor-exec` (which runs them unconfined if the profile isn't loaded): the services' conf.d files source `/usr/libexec/cervino/apparmor-start.sh`, which replaces OpenRC's default `start` (so it only works while the init script doesn't define its own), and the package's `/etc/inittab` wraps the gettys. The serial console getty the initramfs appends to inittab is wrapped by the `lbu` shim, so only on installed systems. Helpers a daemon runs either stay in its profile (`ix`), or run unconfined (`Ux`) when they are the user's session, a login or service control (sessions from `gdm-session-worker`, jobs from crond, poweroff from elogind, D-Bus activation through `dbus-daemon-launch-helper`, after which each service attaches to its own profile). Every profile accepts signals from `peer=busybox`: root's shells (and `rc-service`, `kill`, `killprocs` run from them) carry the label of Alpine's unconfined-mode `busybox` profile, not `unconfined`, which `abstractions/base` already lets in. Alpine's `dbus-daemon` has no AppArmor support and the kernel doesn't mediate Unix sockets, so the profiles have no `dbus` or `unix` rules.

To work out what a daemon needs, load its profile with `flags=(complain)`, exercise it, and collect the `apparmor="ALLOWED"` lines from `dmesg` (the image's kernel arguments keep them from being dropped); then check for `apparmor="DENIED"` in enforce mode. `apparmor_parser -QT -K <file>` in an Alpine container checks a profile's syntax.
